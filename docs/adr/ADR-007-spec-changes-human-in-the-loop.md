# ADR-007: Изменение спецификаций — только после согласования (Human-in-the-loop)

## Status
Accepted (2026-07-31)

## Context

Проект работает по SDD (Spec-Driven Development): спеки в `docs/` (PRD, SPEAKING_TRAINER_SPEC_PART1–3) и `openspec/` — источник истины, версионируются и ревьюятся (AGENTS.md правило 5, ADR принят 2026-07-31 вместе с внедрением OpenSpec).

При реализации Фазы 1 (SPEAKING-TRAINER backend) агент обнаружил внутреннее противоречие спеки Part 1 (DDL `SMALLINT` vs JPA `Int` → Hibernate validate падал) и **самостоятельно** исправил спеку (bump v1.0 → v1.1) до кода. Владелец указал, что решения об изменении спеки — его прерогатива: агент не должен менять контракты, даже для устранения очевидных противоречий, без явного согласования.

Риск автономных правок спек: агент может «решить» за владельца продуктовый или контрактный вопрос (а не только техническую опечатку), и кодовая база уедет за непроверенным решением.

## Decision

**Любое изменение спеки/PRD (major, minor и patch версии) выполняется только после явного согласования с пользователем (human-in-the-loop).**

Процесс для агента:
1. Обнаружив расхождение/противоречие в спеке, агент **останавливает реализацию затронутого участка** и формулирует предложение: что меняется, почему, какие альтернативы, влияние на другие спеки (Part 1 ↔ Part 2 ↔ Part 3 ↔ PRD).
2. Пользователь подтверждает (или выбирает альтернативу) — только после этого агент вносит правку с bump версии и строкой в ченджлоге, затем продолжает реализацию.
3. Исключений нет — включая «технические» patch-правки и устранение внутренних противоречий спеки.
4. Правило фиксируется в AGENTS.md (правило 5) и действует на все спеки: `docs/`, `openspec/specs/`, delta-specs в `openspec/changes/`.

## Consequences

### Positive
- Контракты продукта меняются только осознанным решением владельца.
- Спека остаётся доверенным источником: любое её состояние — согласованное.
- Предложения об изменении проходят кросс-проверку влияния на смежные спеки до правки.

### Negative
- Реализация приостанавливается на время согласования (latency на мелких patch-правках).
- Агент обязан явно формулировать предложения вместо «тихих» исправлений — больше дисциплины в коммуникации.

## Alternatives Considered

### Alternative 1: Автономные patch-правки, согласование только minor/major
Агент правит опечатки и внутренние противоречия сам, согласует только изменения требований.

**Why rejected:** граница «patch vs minor» субъективна; противоречие SMALLINT/Int казалось техническим, но это всё равно изменение контракта данных. Владелец выбрал полный контроль.

### Alternative 2: Править код молча, спеку обновлять постфактум
Код вперёд, спека догоняет.

**Why rejected:** прямое нарушение SDD — спека перестаёт быть источником истины; уже отвергнуто AGENTS.md правилом 5.
