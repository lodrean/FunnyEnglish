# client-logging Specification

## Purpose
Сквозной сбор диагностических логов: клиентские приложения (Android/desktop/WASM/admin-web)
отправляют записи уровня WARN/ERROR на backend, backend хранит их в БД и отдаёт администратору
для просмотра и фильтрации в admin-web.
## Requirements
### Requirement: Приём клиентских логов

Система SHALL принимать пакеты логов через `POST /api/public/logs` без аутентификации
(публичный доступ, как guest-events). Тело — объект `{ "logs": [...] }`, размер пакета от 1 до 50
записей. Каждая запись: `timestamp` (ISO-8601 с зоной), `level` (`WARN`|`ERROR`), `tag`,
`message`, опционально `stackTrace`, `platform` (`android`|`desktop`|`wasm`|`admin-web`),
`appVersion`, `anonymousId` (UUID).

Система SHALL отбрасывать невалидные записи (невалидный UUID/уровень/дата, превышение лимитов
длины) и сохранять валидные — «клиенту не доверяем». Ответ — `200 OK` с числом принятых записей
`{ "accepted": N }`. Система SHALL NOT отклонять весь пакет из-за части невалидных записей.

Система SHALL обрезать `message` и `stackTrace` до лимитов хранения (4 КБ и 16 КБ
соответственно) вместо отказа.

#### Scenario: Валидный пакет принят

- **WHEN** клиент отправляет `POST /api/public/logs` с пакетом из 3 валидных записей WARN/ERROR
- **THEN** все 3 записи сохраняются в БД и ответ содержит `accepted: 3`

#### Scenario: Часть записей невалидна

- **WHEN** пакет содержит 2 валидные записи и 1 запись с невалидным `anonymousId`
- **THEN** сохраняются 2 записи, ответ `200` с `accepted: 2`, ошибки нет

#### Scenario: Превышение размера пакета

- **WHEN** пакет содержит 51+ записей или 0 записей
- **THEN** ответ `400 Bad Request`, ничего не сохраняется

#### Scenario: Доступ без токена

- **WHEN** запрос отправлен без заголовка Authorization
- **THEN** запрос обрабатывается (эндпоинт публичный), rate limiting применяется на уровне IP

### Requirement: Хранение логов

Система SHALL сохранять логи в таблицу `client_logs` с полями: идентификатор, anonymous_id
(NULL допустим), level, tag, message, stack_trace (NULL допустим), platform, app_version,
client_timestamp, created_at (серверное время приёма). Должны существовать индексы по
`created_at`, `level`, `anonymous_id` для выборок админки.

#### Scenario: Серверное время приёма фиксируется

- **WHEN** запись с `client_timestamp` из прошлого сохраняется
- **THEN** `created_at` отражает момент приёма на сервере, `client_timestamp` сохраняется как передан

### Requirement: Просмотр логов администратором

Система SHALL предоставлять `GET /api/admin/logs` только пользователям с ролью ADMIN.
Параметры: `level`, `platform`, `from`, `to` (диапазон created_at), `q` (подстрока в message),
`page`, `size`. Ответ — постраничный список, сортировка по `created_at` DESC.

#### Scenario: Администратор фильтрует ошибки Android

- **WHEN** ADMIN запрашивает `GET /api/admin/logs?level=ERROR&platform=android&page=0&size=20`
- **THEN** возвращается страница записей только level=ERROR и platform=android, свежие первыми

#### Scenario: Не-администратор отклонён

- **WHEN** запрос выполняет пользователь без роли ADMIN или аноним
- **THEN** ответ `403` (для анонима — по общей политике безопасности), данные не возвращаются

### Requirement: Клиентская очередь и отправка

Клиент SHALL складывать записи уровня WARN и выше в локальную персистентную очередь
(переживает перезапуск). Ёмкость ограничена двумя лимитами (срабатывает первый): 200 записей
и 7 КБ сериализованного JSON (платформенный лимит java.util.prefs 8192 символа на desktop);
при переполнении вытесняется старейшая запись, новейшая не вытесняется никогда. Поля записи
обрезаются при постановке (message 1000 / stackTrace 2000 символов).
Клиент SHALL отправлять накопленные записи батчами до 50 при наличии сети: при старте
приложения и после добавления новой записи. Очередь очищается только после успешного ответа
сервера. Ошибка отправки SHALL NOT порождать новую запись в лог (защита от рекурсии) и
не влияет на UX.

Клиент SHALL NOT включать в отправляемые записи тела сетевых запросов, токены и пароли.

#### Scenario: Офлайн-накопление

- **WHEN** на устройстве без сети происходит 3 ошибки уровня ERROR
- **THEN** 3 записи сохраняются локально и отправляются при появлении сети

#### Scenario: Переполнение очереди

- **WHEN** очередь заполнена до лимита (200 записей или 7 КБ JSON) и добавляется новая запись
- **THEN** старейшие записи вытесняются до вписывания в лимиты, новейшая запись сохраняется

#### Scenario: Сбой отправки

- **WHEN** отправка пакета завершается сетевой ошибкой
- **THEN** записи остаются в очереди, пользователь ничего не замечает, новых логов об этом сбое не создаётся

### Requirement: Серверное файловое логирование и access-log

Backend SHALL дублировать логи в файл с ротацией (размер/история настраиваются, дефолт
10 МБ × 7 файлов) и SHALL писать access-log каждого HTTP-запроса (метод, путь, статус,
длительность) без тел запросов/ответов. Health-check путь SHALL исключаться из access-log.

#### Scenario: Запрос отражён в access-log

- **WHEN** выполнен `GET /api/public/speaking/libraries`, завершившийся 200 за 35 мс
- **THEN** в логе backend есть строка с методом, путём, статусом 200 и длительностью; тело ответа не логируется
